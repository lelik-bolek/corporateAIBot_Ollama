# corporateAIBot_Ollama (v3) — Гибридный RAG с BM25 + Dense + RRF

Учебный инженерный проект по исследованию и практической реализации сквозного конвейера **RAG (Retrieval-Augmented Generation)** с гибридным поиском (**BM25 + Dense + Reciprocal Rank Fusion**), интеграции локальных больших языковых моделей (**LLM**), построению трехуровневой системы безопасности (**Security Guardrails**), а также разработке отказоустойчивой, наблюдаемой (**Observability**) архитектуры на базе двойного контура логирования.

---

## 1. Назначение и учебные цели проекта

Проект создан как прикладной исследовательский стенд для освоения технологий искусственного интеллекта и системной инженерии:

- **Исследование гибридного RAG (Dense + BM25 + RRF):** изучение механизмов семантического поиска (плотные эмбеддинги E5), разрежённого поиска (BM25Okapi с морфологическим стеммингом) и слияния рангов (Reciprocal Rank Fusion, k=60) для гарантированного нахождения как синонимичных, так и точных технических терминов.

- **Гарантия честной работы RAG:** чтобы исключить ответы модели «по памяти» и гарантировать опору исключительно на индекс, база знаний наполнена корпоративными руководствами по проектированию потоков **Apache NiFi** (15 PDF из Confluence), содержащими специфические термины (`GenerateFlowFile`, `PutDatabaseRecord`, `Back Pressure`, `${UUID}`), отсутствующие в предобучении модели.

- **Отказоустойчивость и стабильность пайплайна:** подавление зацикливаний генерации (штрафы за повторы `repeat_penalty: 1.15`), предотвращение обрыва рассуждений (лимиты токенов, сжатый CoT в 1–2 предложения), защитные механизмы отсечения оффтопа по косинусному порогу.

- **Эшелонированная безопасность (Security Guardrails):** моделирование сценариев атак (включая *Indirect Prompt Injection* через вредоносный файл `security_test_canary.txt` с канареечным токеном `swordfish`), перехват прямых инъекций на входе, изоляция контекста тегами `<КОНТЕКСТ>` и верификация опоры ответа на контекст (*Grounding Verification*).

- **Прозрачная наблюдаемость (Observability & Telemetry):** отказ от непрозрачных «черных ящиков» в пользу инженерного аудита и сбора метрик.

## 2. Архитектура наблюдаемости: двухпоточная система логирования

В проекте реализована отказоустойчивая система телеметрии без использования тяжелых внешних сервисов (на базе стандартных модулей Python):

1. **Инженерный системный аудит (`logs/system/app.log`):**
	* Обслуживается `RotatingFileHandler` (ротация по 10 МБ, хранение 5 копий) с дублированием в консоль.
	* Фиксирует весь жизненный цикл сервиса: старт ChromaDB, загрузку SentenceTransformer, подключение к Ollama, входящие HTTP-запросы с Correlation ID (`X-Trace-ID`), предупреждения ИБ (`[Security Alert]`, `[Security Block]`) и полные Stack Trace ошибок HTTP 500.

2. **Продуктовая телеметрия качества RAG (`logs/eval/eval_runs_v3.jsonl`):**
	* Асинхронно дописывается через `FastAPI BackgroundTasks` после отправки ответа клиенту.
	* Построчно сохраняет сериализованные JSON-слепки взаимодействий: `request_id`, запрос, ответ, скрытую цепочку рассуждений (`chain_of_thought`), источники, флаги `is_known` и `security_triggered`, скоры сходства и изолированные задержки:

	* `retrieval_latency_ms` — суммарная задержка гибридного поиска (Dense ChromaDB + Sparse BM25 + RRF);

	* `llm_latency_ms` — время инференса и токенизации Ollama;

	* `total_latency_ms` — общее время обработки конвейера;

	* `bm25_top_score` — максимальный сырой балл BM25 среди всех документов;

	* `bm25_matches_count` — количество чанков из ветки BM25, вошедших в финальный `FINAL_TOP_K`.

## 3. Технологический стек

| Слой / Компонент | Технология | Назначение в проекте |
| --- | --- | --- |
| **API & Бэкенд** | Python 3.11+, FastAPI, Uvicorn, Pydantic v2 | Асинхронный REST API (`/ask`, `/health`), Trace Middleware, фоновые очереди.|
| **Векторное хранилище** | **ChromaDB** (`PersistentClient`) | Локальная база данных (SQLite + Parquet в папке `chroma_db/`), хранящая векторы, метаданные и текст чанков.|
| **Разрежённый поиск** | **BM25Okapi** (`rank-bm25`) + `nltk` (SnowballStemmer) | Точный текстовый поиск по техническим идентификаторам. Индекс сериализован в `chroma_db/bm25_index.pkl`.|
| **Слияние рангов** | **Reciprocal Rank Fusion** (k=60) | Объединение Dense и Sparse результатов без перекоса в пользу любого метода.|
| **Эмбеддер** | `intfloat/multilingual-e5-base` (d=768) | Плотный bi-encoder для качественной семантики на русском языке. Префиксы `passage: ` (для базы) и `query: ` (для поиска).|
| **Инференс LLM** | **Ollama** + `qwen2.5:1.5b-instruct` | Локальный C++ движок (llama.cpp) для исполнения квантованных моделей без обращений к облачным API.|
| **Безопасность** | `src/security/` (Guardrails) | Регулярные выражения инъекций, фильтрация CoT, очистка чанков, чекер `verify_grounding`.|
| **Анализ телеметрии** | `tools/analysis/latency_calculator.py` | Внутренняя утилита расчета P50 / Среднего / P95 времени отклика в разрезе дат и версий логов. |
| **Контейнеризация** | Docker & Docker Compose | Изолированный запуск связки «API + Ollama» с сохранением томов данных и логов.|

## 5. Особенности кроссплатформенности и синхронизации (Windows ↔ Mac M4)

Проект изначально разработан с учетом одновременной кроссплатформенной работы на машинах с разными архитектурами через общий Git-репозиторий:

1. **Разделение оборудования:**
- **Windows (Intel Core i5, 16 GB RAM):** запуск на базе инструкций AVX2 (задержка инференса LLM ~15–35 секунд).
- **macOS (Apple Silicon M4, 16 GB RAM):** нативное ускорение Ollama через Metal GPU и объединенную память (задержка генерации ~2–4 секунды).


2. **Пути файловой системы (`pathlib.Path`):**
* Полностью исключен хардкод системных разделителей (`/` или `\`).
* Все пути в `src/config.py` строятся от базового `BASE_DIR = Path(__file__).resolve().parent.parent`, что гарантирует одинаковую работу в Windows PowerShell, macOS zsh и Linux Docker.

3. **Изоляция бинарных данных и виртуальных сред:**
* Каталоги `.venv/` и `chroma_db/` занесены в `.gitignore`. При переходе между ОС достаточно подтянуть код через `git pull` и выполнить команду перестроения индекса:

```bash
python -m src.build_index

```

4. **Сетевые конфигурации:**
* Переменная `OLLAMA_HOST` параметризована через `src/config.py` и переменные окружения: при локальном запуске используется `http://localhost:11434`, внутри сети Docker Compose — `http://ollama_service:11434`.

## 6. Краткий порядок запуска

Полные инструкции по мониторингу, эксплуатации и сценариям тестирования приведены в [`docs/runbook/README.md`](docs/runbook/README.md).

### Быстрый старт на хосте (Windows / macOS)

1. Запустите демон **Ollama** и скачайте рабочую модель:

```bash
ollama pull qwen2.5:1.5b-instruct

```

2. Установите зависимости и соберите векторную базу знаний:

```bash
pip install -r requirements.txt
python -m src.build_index

```

3. Запустите API-сервер:


```bash
python -m uvicorn src.bot:app --host 127.0.0.1 --port 8000

```


Документация и тестирование Swagger UI: `[http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)`.

### Анализ метрик задержки

Для запуска сводного отчета по собранным журналам выполните утилиту:

```bash
python tools/analysis/latency_calculator.py

```

*(Утилита автоматически найдет все журналы в `logs/eval/`, сгруппирует запросы по дням и версиям и выведет P50 / Ср / P95 задержек поиска и LLM).*


### Запуск API-сервера:
python.exe -m uvicorn src.bot:app --host 127.0.0.1 --port 8000
