Restricted Components Оглавление: Ограниченные компоненты (Restricted Components) Почему это важно? Как это работает в интерфейсе? Политики ограниченных компонентов Заключение Ограниченные компоненты (Restricted Components) В Apache NiFi компоненты (такие как процессоры, сервисы контроллера и т.д.) являются точками расширения, которые могут выполнять широкий спектр действий. Большинство из них работают в рамках стандартной модели безопасности, обрабатывая данные FlowFiles.

Однако существует особая категория — Ограниченные компоненты (Restricted Components). Это компоненты, которые по своей природе обладают повышенными привилегиями и могут выходить за пределы стандартного изолированного окружения NiFi.

Как указано в документации: Это компоненты, которые могут использоваться для выполнения произвольного, непроверенного кода, предоставленного оператором через REST API/UI NiFi, или для получения или изменения данных на host NiFi с использованием учетных данных операционной системы, под которыми запущен NiFi. Такие компоненты могут быть использованы авторизованным пользователем NiFi для выхода за пределы предполагаемого использования приложения, повышения привилегий или раскрытия данных о внутреннем устройстве процесса NiFi или host системы.

Почему это важно? Из-за не ограниченного уровня доступа такие компоненты представляют потенциальную угрозу безопасности. Поэтому работа с ними требует явного предоставления прав. Как это работает в интерфейсе? 1. Визуальная маркировка: При добавлении процессора на полотно, ограниченные компоненты отмечаются специальным значком щита рядом с названием.

2. Подсказка с требованиями: При наведении курсора на этот значок (во время выбора процессора), интерфейс показывает, какое именно ограничение (или набор ограничений) требуется для использования данного компонента. Например, процессор ExecuteProcess требует права execute code.

3. Управление доступом: Пользователь не сможет воспользоваться процессором этого типа и/или его настройками, если ему не назначены соответствующие политики безопасности. Это регулируется политикой access restricted components (доступ к ограниченным компонентам), которая может быть выдана как: «Без учёта ограничений» (regardless of restrictions): Пользователь получает доступ ко всем ограниченным компонентам.

«На отдельные ограничения» (specific restrictions): Пользователь получает доступ только к компонентам, требующим определенный набор прав (например, только read filesystem и write filesystem). Политики ограниченных компонентов Ниже представлен полный перечень политик, которые могут требоваться для работы с ограниченными компонентами. Администратор назначает эти права пользователям или группам, определяя, с какими именно «опасными» возможностями они могут работать.

Политика (англ.) Технический перевод Описание и контекст regardless of restrictions без учёта ограничений Политика, дающая пользователю полный и безусловный доступ ко всем существующим и будущим ограниченным компонентам, минуя проверки по отдельным категориям.

requiring 'access environment credentials' требуется 'доступ к учетным данным окружения' Компоненту необходим доступ к переменным окружения операционной системы, в которой запущен процесс NiFi. requiring 'access keytab' требуется 'доступ к keytab-файлу' Требуется доступ к keytab-файлу (файлу ключей), используемому для аутентификации в протоколе Kerberos.

requiring 'access ticket cache' требуется 'доступ к кешу ticket' Требуется доступ к ticket cache, где хранятся активные ticket аутентификации Kerberos. requiring 'execute code' требуется 'возможность выполнения кода' Компонент может выполнять произвольный код (например, скрипты на Python, Groovy, или запускать внешние процессы), что является одним из наиболее привилегированных действий.

requiring 'export nifi details' требуется 'экспорт внутренних деталей NiFi' Компонент может раскрывать конфиденциальную информацию о внутреннем состоянии экземпляра NiFi (конфигурацию, метаданные, потоки данных), которая не предназначена для внешних потребителей.

requiring 'read distributed filesystem' требуется 'чтение из распределенной файловой системы' Необходимо право на чтение данных из распределенной файловой системы (например, HDFS, Amazon S3, Azure Blob Storage).* requiring 'read filesystem' требуется 'чтение файловой системы' Необходимо право на чтение файлов из локальной файловой системы сервера, на котором работает NiFi.* requiring 'reference remote resource' требуется 'обращение к удаленному ресурсу' Компонент может динамически обращаться к внешним сетевым ресурсам, чей адрес или параметры соединения не фиксированы жестко в конфигурации.

requiring 'write distributed filesystem' требуется 'запись в распределенную файловую систему' Необходимо право на запись данных в распределенную файловую систему (например, HDFS, Amazon S3, Azure Blob Storage). requiring 'write filesystem' требуется 'запись в файловую систему' Необходимо право на запись данных в *локальную* файловую систему сервера, на котором работает NiFi.

*В документации разделяются права на работу с распределенными файловыми системами (HDFS, S3 и т.д.) и с локальной файловой системой сервера, где запущен NiFi. Заключение Ограниченные компоненты — это мощный, но потенциально опасный инструмент. Их использование должно быть строго регламентировано. Понимание перечисленных выше политик позволяет администраторам безопасности точно настраивать права доступа, следуя принципу наименьших привилегий (least privilege): предоставлять пользователям ровно те возможности, которые необходимы им для выполнения их задач, и не более того. Всегда проверяйте значок рядом с компонентом перед его добавлением в поток данных и убедитесь, что его использование оправдано и безопасно.
