Цель: контролируемое управление доступом; разделение ответственности между ролями; предсказуемость изменений в системе. Общие принципы Потоки Apache NiFi являются критической частью инфраструктуры обработки данных и могут содержать: конфигурации интеграций; конфиденциальные данные; учетные данные для доступа к внешним системам.

В связи с этим управление доступом должно быть централизованным и строго регламентированным. NiFi реализует модель multi-tenant authorization, где доступ определяется политиками, назначенными на ресурсы и компоненты. Базовые принципы Минимальные привилегии (PoLP) Пользователь получает только те права, которые необходимы для выполнения задач.

Доступ через группы Права назначаются группам, а не пользователям. Наследование политик доступа Политики наследуются от родительского ресурса к дочернему, если на дочернем ресурсе не задана собственная политика. Например, если группе предоставлен доступ к группе процессов, этот доступ распространяется на все компоненты внутри неё.

Если политика на родительском уровне удаляется, доступ сохраняется только в случае, если на дочернем уровне заданы собственные политики. Модель авторизации в NiFi Типы политик доступа NiFi использует два уровня политик: View — Если для ресурса создана политика просмотра, только пользователи или группы, добавленные в эту политику, могут видеть детали этого ресурса.

Modify — Если у ресурса есть политика изменения, только пользователи или группы, добавленные в эту политику, могут менять конфигурацию этого ресурса. Глобальные политики Определяют доступ к системе в целом. Находятся в главном меню, пункт Policies.

view the user interface — доступ к UI access the controller — доступ к настройкам платформы (Controller Services, Reporting Tasks) access parameter contexts — доступ к контекстам параметров query provenance — доступ к provenance access restricted components — доступ к ограниченным компонентам access all policies — управление политиками access users/user groups — управление пользователями/группами пользователей retrieve site-to-site — доступ к site-to-site view system diagnostics — диагностика системы proxy user requests — проксирование access counters — доступ к счетчикам Политики на уровне компонентов Определяют доступ к конкретным объектам.

Находятся на уровне объектов. view the component - просмотр компонента modify the component - изменение компонента operate the component - управление компонентом view provenance - просмотр происхождения данных view the data - просмотр данных modify the data - изменение данных receive data via site-to-site - получение данных через site-to-site send data via site-to-site - отправка данных через site-to-site view the policies - просмотр политик modify the policies - изменение политик Принципы построения модели доступа Минимальные привилегии Каждая роль получает только необходимые права.

Разделение ответственности Среда Политика DEV создание, изменение, доступ к данным TEST просмотр, ограниченные изменения PROD просмотр, изменения запрещены Это снижает риск влияния на данные. Изоляция критичных функций Критичные операции вынесены в Restricted Components.

Это позволяет: централизованно контролировать риск; ограничить доступ; снизить последствия ошибок. Контроль через Parameter Context Доступ к чувствительным данным осуществляется: через централизованные параметры. Разделение ролей Роли разделяются по зонам ответственности: Роль/ Группа Назначение Целевые среды Administrator управление платформой и безопасностью, выдача прав DEV/TEST/PROD Data Engineer разработка и эксплуатация потоков DEV/TEST (ограниченно) Analyst просмотр данных и результатов, ограниченное управление (запуск/ остановка) DEV/TEST Риски неправильной настройки Ошибки могут привести к: несанкционированному доступу; выполнению опасных операций; утечке данных; нарушению работы потоков.

Требования: централизованное управление правами; контроль изменений. Ценность модели Снижение ошибок Ограничения не дают: случайно удалить поток, сломать архитектуру, изменить критичные параметры. Снижение утечек Контроль restricted компонентов: исключает несанкционированный доступ к данным; ограничивает работу с файловыми системами и внешними ресурсами.

Управляемость Четкое понимание: кто и что может делать; кто отвечает за изменения; где искать причину проблемы. Ускорение разработки Парадоксально, но ограничения: уменьшают хаос; делают систему предсказуемой; упрощают командную работу.

Упрощение аудита Благодаря разделению ролей: проще понять источник изменений; быстрее локализуются инциденты. Нет меток
