Ключевые этапы обработки данных включают операции, которые: - выполняют извлечение данных из внешних источников; - осуществляют запись данных во внешние системы; - изменяют структуру, семантику или объём данных; - содержат сложную или нестандартную бизнес-логику.

Примеры операций, подлежащих логированию: преобразования, включающие агрегацию, фильтрацию по бизнес-правилам, объединение потоков, JOLT-трансформации и/или скрипты. Примеры операций, для которых отдельное логирование не требуется: технические вспомогательные процессы (например, простые UpdateAttribute, ReplaceText без логики, маршрутизация без вычислений).

Логирование ошибок обязательно для: - всех операций извлечения и записи данных; - всех этапов, где возможна потеря данных или искажение результата; - всех пользовательских и скриптовых преобразований. Локальность логирования - Логирование выполняется для каждого логического этапа отдельно, то есть в каждой Process Group.

- Логи должны обеспечивать изоляцию ответственности и упрощать анализ работы отдельных групп. Формат и атрибуты логирования Для обеспечения однозначной трассировки и возможности централизованного мониторинга необходимо фиксировать ключевые атрибуты FlowFile, такие как: идентификаторы источника, временные метки, количество записей, тип ошибки.

Стандарты логирования должны быть одинаковы во всех группах процессов и соблюдаться во всех потоках проекта. Обработка ошибок Обработка ошибок является обязательной частью проектирования любого потока обработки данных. Поток считается некорректно спроектированным, если в нём не предусмотрена обработка типовых и заранее известных ошибок, характерных для данного сценария. Ошибки в NiFi разделяются по характеру и требуют различного поведения потока.

Ошибки данных (ожидаемые ошибки) К ошибкам данных относятся ситуации, при которых входные данные не соответствуют ожидаемому формату или правилам обработки. Примеры: некорректная структура данных, отсутствие обязательных полей, нарушение типов данных, логически недопустимые значения.

Такие ошибки: - не подлежат повторной обработке без изменения данных, - должны быть изолированы от основного потока, - подлежат логированию с указанием причины отклонения. Возврат таких данных в основной поток запрещён. Временные сбои внешних систем К временным сбоям относятся ошибки, вызванные недоступностью или нестабильной работой внешних систем.

Примеры: временная недоступность базы данных, сетевые сбои, превышение времени ожидания ответа, кратковременные ограничения по нагрузке. Для таких ошибок должен быть предусмотрен механизм повторной попытки обработки с паузами между попытками и ограниченным количеством повторов. При исчерпании допустимого количества попыток выполняется логирование соответствующей ошибки, данные не сохраняются, если иное прямо не предусмотрено логикой Потока.

Стандартная настройка механизмов повторной обработки временных сбоев производится с использованием параметров повторных попыток, пауз и политики ожидания, настраиваемых на вкладке Relationships процессора. Необрабатываемые ошибки выполнения К необрабатываемым ошибкам относятся ситуации, при которых дальнейшая автоматическая обработка данных в рамках текущего потока невозможна без изменения конфигурации или логики обработки. Данные, попавшие в данную категорию: - не участвуют в дальнейшей обработке; - подлежат фиксации с сохранением исходного содержимого и контекста ошибки; - требуют уведомления Заказчика или владельца данных.

Дальнейшие действия с такими данными выполняются после получения от Заказчика подтверждённых указаний, включая, но не ограничиваясь: - изменением правил обработки; - расширением допустимых форматов или значений; - явным решением об исключении данных из обработки.

До получения указаний Заказчика повторная обработка таких данных не целесообразна. Примеры: - Изменение структуры данных источника; - Появление нового типа бизнес-значения. Например: новый статус `REVERSED`; - Изменение бизнес-правил. Например: Было правило: `amount > 0`. Появились записи с `amount = 0`, которые ранее считались ошибкой.

- Конфликт требований. Например: данные проходят валидацию, но целевая система возвращает ошибку бизнес-уровня: «контрагент не зарегистрирован». - Архитектурное ограничение. Например: MergeContent настроен на max 1000 записей, но начал получать по 500 000.

Логирование и трассировка ошибок Для каждой ошибки должно быть зафиксировано: - время возникновения, - этап потока, - идентификатор запуска, - краткое описание причины. Отсутствие информации для трассировки считается дефектом потока.

Стандартный механизм логирования ошибок описан в [Типовые схемы обработки данных](#7-типовые-схемы-обработки-данных). Механизмы повторных попыток Рекомендуется использовать настройку Retry Back Off Policy - Penalize. Для обработки временных сбоев внешних систем не рекомендуется полагаться исключительно на паузы в связях между процессорами (вкладка Relationships).
