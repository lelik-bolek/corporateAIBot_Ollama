Наименование должно отражать назначение потока или его роль в общей интеграции.

Примеры: f_DataIngestionFromCRM, f_LoadToDataLake, f_ReplicationOfDirectory. f_ – Поток (Flow) cs_ - Контроллер-сервисы (Controller Services) pg_ – Процессорная группа (Process Group) PC_ – Переменная контекста (Parameter Context) a_ – Атрибут (FlowFile Attribute) t_ – Атрибут для проведения тестов (FlowFile Attribute). После завершения тестирования удаляется.

Процессорная группа (Process Group) Наименование должно отражать функциональную роль группы. Стиль: PascalCase Примеры: pg_MergeSearchResults, pg_TransformPets Процессоры Название должно четко описывать действие процессора (глагол + существительное).

Стиль: PascalCase Примеры: ExtractJsonAttributes, DeduplicateCluster, ValidatePassportFormat - если используется дополнительная вкладка, к примеру, UpdateAttribute вкладка Advanced, то в названии указываем [A]. Примеры: RouteOnAttribute[A], IdentifyCustomer[A].

Порты (Input/Output Ports) Должны указывать направление передачи данных. Стиль: lower_snake_case Примеры: in_start, out_success, out_error Параметры контекста (Parameter Context) Глобальные константы и настройки среды. Стиль: SCREAMING_SNAKE_CASE Примеры: DATABASE_HOST, INPUT_DIRECTORY_PATH, KAFKA_TOPIC_NAME.

Контроллер-сервисы (Controller Services) Префикс: cs_. Постфикс: _default используется если сервис является стандартным, или отражает особенность обработки данных: _avro (использует механизм avro-schema). Область действия: сервисы должны объявляться на корневом уровне потока (Flow) для использования во всех логических группах одного потока (принцип наследования).

Примеры: cs_DBCPConnectionPool_Avro, cs_SSLContextService_Default. Атрибуты (FlowFile Attributes) Стиль: lower_snake_case Примеры: a_file_name, a_record_count, a_is_valid Запрещены: - аббревиатуры без расшифровки, - технические имена без бизнес-смысла.

Объявление обязательных атрибутов В начале каждого потока (GenerateFlowFile, UpdateAttribute) необходимо объявить следующий набор атрибутов для обеспечения логирования: - a_developer: Ivanov (Разработчик) - a_flow_folder: NiFi Flow » ATHENA (папка в которой лежит Поток) - a_flow_name: NiFi Flow » ATHENA » f_ExampleFlow (Наименование потока + путь NiFi) - a_id_run_flow: ${UUID} (Функция генерации UUID) - a_task_number: INF-167 (Номер задачи в Джира) Правила визуального оформления Общие правила расположения элементов Поток данных должен быть построен сверху вниз. Обратная схема движения (например, для повторного запуска процессора по условию) должна быть оформлена так, чтобы не нарушать общую визуальную читабельность. Если в потоке есть ветвления или параллельные процессы, рекомендуется располагать их слева направо. Это помогает визуально разделить логику и упрощает понимание потока.

Использование групп процессов (Process Group) Process Group используется для выделения логического этапа обработки данных и логической изоляции логики. В рамках Process Group также осуществляется локальное логирование и обработка ошибок (см. разделы Принципы проектирования потоков и Логирование операций и ошибок).

1. Допускается использование одной группы процессов для всего потока, если поток прост и атомарен. Правила размещения процессоров и групп процессов: 2. Корневой уровень потока должен содержать только стартовые процессоры (источники данных) и основные Process Group, соответствующие крупным логическим этапам. Размещение одиночных процессоров на корневом уровне (кроме стартовых) не рекомендуется.

3. Если логический этап обработки реализуется менее чем тремя процессорами, создавать для них отдельную Process Group необязательно. Такие процессоры можно размещать внутри родительской Process Group, к логике которой они относятся.

4. Повторное использование логики Если фрагмент логики обработки данных может быть востребован в других потоках (например, стандартное обогащение данных, форматирование, валидация), его рекомендуется оформлять как отдельный Process Group с чётким входом/выходом и параметризуемым поведением.

Такой подход позволяет версионировать, тестировать и переиспользовать общую логику независимо в разных потоках обработки данных. Цветовая маркировка этапов Необходимо использовать цветовую маркировку для визуального обозначения семантики этапов обработки: - желтый (#ffff00) - процессоры взаимодействующие с внешними системами; - синий (#ade8ff) - процессоры условий; - красный (#e32222) - процессор для записи ошибок.

Использование комментариев и Label Комментарии в Process Group размещаются на вкладке General → Comments. Они предназначены для пояснения назначения группы процессов (при необходимости), описания её входов и выходов, ограничений и бизнес-логики, охватывающей весь логический этап. Эти комментарии должны давать обзор того, что делает группа в целом, без детализации отдельных процессоров.

Комментарии внутри процессоров используются для пояснения работы конкретного процессора (при необходимости). Если изменена стандартная логика поведения процессора, для процессоров использующих скрипты, или сложные трансформации. Комментарии размещаются во вкладке Comments каждого процессора и должны давать понимание его особенностей.

Label — отдельный элемент схемы NiFi, который можно использовать для визуальных пояснений (при необходимости), маркировки блоков, этапов или потоков, особенно когда нужно добавить пояснение для логической группы. Рекомендованный стиль: фон #fff7d7, шрифт 16px.

Рекомендуемое разделение комментариев: - Process Group: назначение группы, входы/выходы, бизнес-логика, ограничения; - Процессор: детали конкретной обработки, алгоритмы, особенности обработки; - Label: визуальные пояснения, объединяющие несколько элементов, напоминания для команды, краткие инструкции.

Работа с данными и атрибутами В Apache NiFi данные перемещаются в виде сообщений FlowFile, состоящих из тела сообщения (Content) и набора атрибутов (Attributes). Корректное разделение ответственности между ними является обязательным условием стабильной и масштабируемой работы потоков.

Тело сообщения В теле сообщения (Content) должны храниться: исходные данные, преобразованные данные, данные, предназначенные для передачи в целевую систему. В тело сообщения не допускается вынос служебной информации, за исключением случаев объективно требующих данного функционала.

Атрибуты В контексте данного документа атрибутами считаются все атрибуты FlowFile, как системные - создаваемые системой, так и добавляемые разработчиком - пользовательские. Атрибуты используются для: управления логикой обработки, маршрутизации данных, логирования и трассировки, передачи технического контекста выполнения.

NiFi не различает системные и пользовательские атрибуты по принципу хранения и обработки, поэтому требования данного раздела применяются ко всем атрибутам без исключения. Обязательные атрибуты В каждом потоке обработки данных имеется набор атрибутов, необходимых для эксплуатации и сопровождения потока, независимо от бизнес-логики. К обязательным относятся атрибуты, указанные в п. объявление-обязательных-атрибутов.

Отсутствие обязательных атрибутов считается нарушением стандарта. Область действия атрибутов Атрибуты должны иметь ограниченную область действия. Рекомендуется: - использовать атрибуты только внутри логического этапа, где они необходимы; - не передавать временные и диагностические атрибуты за пределы соответствующей группы процессов; - не использовать атрибуты для передачи бизнес-данных.

Управление жизненным циклом атрибутов Создание атрибута должно быть обусловлено явной необходимостью. После выполнения своей функции атрибуты рекомендуется удалять. За исключением атрибутов указанных в п. объявление-обязательных-атрибутов.

Удаление атрибутов является осознанной операцией оптимизации и направлено на: снижение потребления памяти, уменьшение размера очередей, повышение устойчивости системы при массовой обработке данных. Ограничения и запреты Запрещается: - бесконтрольное добавление атрибутов; - дублирование атрибутов (одинаковая смысловая нагрузка, повторное создание без необходимости, избыточность значений); - накопление атрибутов, не используемых в дальнейшей логике потока; - использование атрибутов для хранения больших объёмов данных, объемом более 100 kB.
