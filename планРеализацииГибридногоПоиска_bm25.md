
### Краткая сводка по текущему боту (из истории проекта)

* **Проект:** `corporateAIBot_Ollama` (v3) — локальный, полностью изолированный автономный RAG-сервис на FastAPI.
* **Текущий стек:**
* **LLM Engine:** Ollama (`qwen2.5:1.5b-instruct`, квантование INT4/INT8, C++/AVX2/Metal).
* **Dense Embedder:** `intfloat/multilingual-e5-base` (d=768, префиксы `passage: ` и `query: `).
* **Vector DB:** `ChromaDB` (`PersistentClient`, косинусное расстояние, хранение в `chroma_db/`).
* **Безопасность и наблюдаемость:** 3 рубежа защиты (Guardrails, фильтрация CoT, санитизация инъекций) + двухпоточное логирование (`app.log` и `eval_runs_v3.jsonl`).
* **Текущая база:** Вымышленная вселенная Star Wars / Aetheria (30+ файлов `.txt`, `terms_map.json`, `poisoned_root.txt`).

### Архитектурная концепция гибридного поиска (BM25 + DENSE (Смысл) + СЛОЙ СЛИЯНИЯ РАНГОВ (RRF))

```text
                           ВХОДЯЩИЙ ЗАПРОС
                                  │
          ┌───────────────────────┴───────────────────────┐
          ▼                                               ▼
[ВЕТКА 1: DENSE (Смысл)]                       [ВЕТКА 2: SPARSE (Точные совпадения)]
• query: + multilingual-e5-base                • Токенизация (regex / слова без стоп-слов)
• ChromaDB ANN Search                          • rank-bm25 (BM25Okapi)
• Top-K_dense кандидатов                       • Top-K_sparse кандидатов
          │                                               │
          └───────────────────────┬───────────────────────┘
                                  │
                                  ▼
                    [СЛОЙ СЛИЯНИЯ РАНГОВ: RRF]
               RRF_Score(d) = Σ [ 1 / (k + Rank(d)) ]  (где k=60)
                                  │
                                  ▼
                   [Финальный Top-3..5 чанков]
                                  │
                                  ▼
                       Промпт ➔ Ollama (LLM)

```

#### Этап 3. Двойная индексация: Dense (ChromaDB) + Sparse (BM25) (`src/build_index.py`)

1. **Токенизатор для BM25 с поддержкой русской морфологии:**
   * Реализовать функцию `tokenize_for_bm25(text: str) -> list[str]`:
     * Выделение токенов через regex: слова, имена параметров, коды, латиница, кириллица.
     * Если токен содержит кириллицу — применять `SnowballStemmer("russian").stem(token)`.
     * Если токен содержит латиницу, цифры или спецсимволы (названия процессоров, порты, параметры) — приводить к `lower()` без искажения основы.

2. **Построение двух индексов за один проход:**
   * Прочитать нормализованные текстовые файлы из `data/knowledge_base/` и файл проверки безопасности с канарейками.
   * Нарезать на чанки по 800 символов с нахлестом 150 символов, присвоив уникальный сквозной `chunk_id`.
   * **Dense:** рассчитать эмбеддинги `multilingual-e5-base` с префиксом `passage: ` и записать в ChromaDB (`PersistentClient`).
   * **Sparse:** сформировать токенизированный корпус чанков через `tokenize_for_bm25`, обучить `BM25Okapi(tokenized_corpus)` и сохранить связку `{index: bm25, chunks: chunk_mapping}` в `chroma_db/bm25_index.pkl`.


#### Этап 4. Онлайн-контур: гибридный поиск и RRF (`src/rag_pipeline.py`)

1. **Инициализация BM25 в рантайме:**
* При старте `RAGPipeline` загружать скомпилированный `bm25_index.pkl` в оперативную память.

2. **Параллельный / составной retrieval:**
* **Dense:** Запрос с `query: ` кодируется через E5 -> запрос в `collection.query()` -> получение `Top-K_dense`.
* **Sparse:** Запрос токенизируется тем же правилом -> `bm25.get_scores()` -> выбор индексов с максимальным скором `Top-K_sparse`.

3. **Реализация слоя слияния (Reciprocal Rank Fusion):**
* Реализовать функцию `reciprocal_rank_fusion(dense_results, sparse_results, k=60)`:

text{RRF_Score}(d) = sum_{m in {text{dense}, text{sparse}}} frac{1}{k + text{rank}_m(d)}

* Отсортировать объединенный пул чанков по `RRF_Score` и отобрать финальные 3–4 чанка.


#### Этап 4. Онлайн-контур: гибридный поиск и слияние рангов (`src/rag_pipeline.py`)

1. **Загрузка индекса:**
   * При инициализации пайплайна подгружать `bm25_index.pkl` в оперативную память.

2. **Двухпоточный поиск кандидатов:**
   * **Ветка Dense:** вопрос пользователя кодируется через E5 (`query: `) -> запрос в ChromaDB (`n_results=TOP_K_DENSE`).
   * **Ветка Sparse:** вопрос токенизируется через `tokenize_for_bm25` -> расчет баллов `bm25.get_scores()` -> выбор `TOP_K_SPARSE` документов с наивысшим баллом.

3. **Слой слияния рангов (RRF):**
   * Реализовать функцию `reciprocal_rank_fusion(dense_hits, sparse_hits, k=60)`:
     * Расчет RRF-скора: text{RRF}(d) = sum_{m in {text{dense}, text{sparse}}} frac{1}{k + text{rank}_m(d)}
     * Формирование финального списка из `FINAL_TOP_K` чанков с наивысшим рангом.

4. **Адаптация эшелонов безопасности и верификации опоры на контекст:**
   * **Рубеж 1 (Вход):** отсечение попыток извлечения учетных записей и служебных инструкций.
   * **Рубеж 2 (Контекст):** фильтрация чанков файла проверки безопасности при обнаружении канареечных маркеров до сборки промпта.
   * **Рубеж 3 (Выход и верификатор `verify_grounding`):** проверка опоры ответа на контекст Apache NiFi и предотвращение утечки канареек через блок рассуждений (`chain_of_thought`).


#### Этап 5. Телеметрия и наблюдаемость (`src/evaluation/logger.py`)

1. **Доработка формата продуктовых логов (`logs/eval/eval_runs_v3.jsonl`):**
* Сохранить базовую метрику времени `retrieval_latency_ms`.
* Добавить в JSONL-структуру метрики для отслеживания вклада BM25 в гибридный контур:
* **`retrieval_latency_ms` (Задержка поиска, мс)** — суммарное время выполнения полного цикла гибридного поиска: параллельное/последовательное получение Top-K из ChromaDB и BM25, расчет слияния рангов (RRF) и сборка финального списка чанков.
* **`bm25_top_score` (Максимальный балл BM25)** — числовая оценка релевантности лучшего чанка по формуле BM25 (на основе частоты терминов TF и обратной частоты IDF). Позволяет детектировать наличие точных лексических совпадений: значение `0.0` сигнализирует, что ни одного ключевого слова из запроса в базе не найдено, а высокое значение подтверждает точное попадание в термин или код.
* **`bm25_matches_count` (Количество чанков от BM25 в топе)** — целое число от `0` до `FINAL_TOP_K`, отражающее, сколько чанков из итоговой выборки, переданной в языковую модель, попало туда благодаря ветке BM25 (либо эксклюзивно из BM25, либо при одновременном подтверждении через Dense). Метрика наглядно показывает, помог ли точный текстовый поиск собрать контекст для текущего вопроса.


#### Этап 6. Валидация и регрессионное тестирование

1. **Тест на точные буквенно-цифровые токены (зона BM25):**

3. **Тест на оффтоп и безопасность:**
* Проверка отсечения нерелевантных вопросов по порогу уверенности.
